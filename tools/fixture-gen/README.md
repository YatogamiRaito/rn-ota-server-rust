# Fixture generation

The parity fixtures under `tests/fixtures/` are recorded from the **real** npm packages, not
hand-written. That is what makes the parity claim testable: `tests/decision_tests.rs`,
`tests/semver_parity_tests.rs` and `tests/pagination_parity_tests.rs` replay them against the
Rust implementation.

**Which upstream package holds which behaviour matters** — an earlier investigation lost time
looking in the wrong one. The authoritative locations, all at the pinned version:

| Fixture | Generated by | Records | From which package |
| --- | --- | --- | --- |
| `tests/fixtures/decision_fixtures.json` | `tests/generate_decision_fixtures.mjs` | `getUpdateInfo` decisions (appVersion + fingerprint) | `@hot-updater/js` (`dist/index.mjs`), with cohort eligibility from `@hot-updater/core` |
| `tests/fixtures/semver_fixtures.json` | `tests/generate_semver_fixtures.mjs` | `semverSatisfies` + npm `semver` `coerce` | `@hot-updater/plugin-core` and the `semver` package |
| `tests/fixtures/pagination_fixtures.json` | `tests/generate_pagination_fixtures.mjs` | `calculatePagination`, `buildCursorPageQuery`, `createPaginatedResult` | `@hot-updater/plugin-core` (`dist/createDatabasePlugin.mjs`) |
| ″ | ″ | every `GET /bundles` query-parameter rule: `limit`, `page`, `platform`, booleans, repeated arrays, nullable strings, truthy strings | `@hot-updater/server` (`dist/handler.mjs`) |

> **`@hot-updater/server` does NOT implement cursor pagination.** Nothing in it declares
> `supportsCursorPagination`, so `createDatabasePlugin.getBundles` falls through to
> **`getBundlesWithLegacyCursorFallback` in `@hot-updater/plugin-core`**
> (`dist/createDatabasePlugin.mjs:138-186`). That fallback is the real code path for the
> self-hosted server and is what this project must match. `@hot-updater/server` owns only the
> HTTP query-parameter layer (`dist/handler.mjs:134-186`).

`tests/fixtures.json` (cohort/hash vectors) is checked in as static data and has no generator.

## Running the generators

The generators import the upstream packages, so they need a `node_modules` that resolves them.
This directory exists to provide one:

```bash
cd tools/fixture-gen && npm ci && cd ../..
```

Use `npm ci`, not `npm install`: it installs strictly from `package-lock.json`, which is what
guarantees the fixtures are regenerated against the same upstream tree they were recorded from.
`npm install` is free to resolve a newer version and would silently move ground truth.

Then run the generators from the repository root — no environment variables needed:

```bash
node tests/generate_decision_fixtures.mjs   > tests/fixtures/decision_fixtures.json
node tests/generate_semver_fixtures.mjs     > tests/fixtures/semver_fixtures.json
node tests/generate_pagination_fixtures.mjs > tests/fixtures/pagination_fixtures.json
```

> Note: these commands used to be documented as `NODE_PATH=tools/fixture-gen/node_modules
> node ...`, which does not work. Node's **ESM** resolver ignores `NODE_PATH` — it only ever
> applied to CommonJS `require` — and ESM resolution walks up from the *importing file*
> (`tests/`), not from the cwd, so no combination of `NODE_PATH` and working directory can
> make a bare specifier resolve. All three generators therefore fall back to importing
> `tools/fixture-gen/node_modules/...` by explicit path when the bare specifier raises
> `ERR_MODULE_NOT_FOUND`.

The generators are deterministic: the case order is fixed and nothing is timestamped or
randomized, so re-running one must produce a byte-identical file. That is what makes
`git diff tests/fixtures/` a reliable upgrade-detection mechanism.

## When to regenerate

Only when upgrading the upstream hot-updater version. Then:

```bash
git diff --stat tests/fixtures/
```

- **Empty diff** — upstream behavior did not change; nothing to do.
- **Formatting-only diff** — leave the files alone.
- **Semantic diff** (an `expected` value changed) — upstream changed its behavior. Do not "fix"
  the fixtures: update the Rust implementation until `cargo test` is green again, and record the
  change in `docs/upstream-parity.md`.

## Pinning

`package.json` here pins the upstream version the fixtures were recorded from — **every**
dependency is an exact version, with no `^` or `~` ranges. Bump one deliberately as part of an
upgrade, never incidentally.

`package-lock.json` is **committed on purpose and is part of the parity claim.** It pins the
transitive tree that produced the checked-in fixtures — including `verkit`, whose exact
resolution the semver fixtures depend on. Do not delete it and do not add it to `.gitignore`:
without it, `npm ci` cannot work and a regeneration could quietly record different upstream
behaviour than the fixtures claim.

`@hot-updater/server` is a dependency only because the query-parameter helpers
(`parsePositiveIntegerSearchParam`, the `page`/`platform`/array rules) are not exported: the
pagination generator drives the real `createHandler()` with a stub api and reads the resulting
400 body, rather than reimplementing them. It is **not** the source of the cursor-pagination
behaviour — see the note above.

If `node tests/generate_pagination_fixtures.mjs` fails with `ERR_MODULE_NOT_FOUND` for
`@hot-updater/server`, a pre-existing warm `node_modules` predates that dependency; re-run
`npm ci` in this directory.

## A note on the pagination fixtures

`buildCursorPageQuery` and `createPaginatedResult` are module-private in `@hot-updater/plugin-core`.
The generator does not reimplement them: it hands the public `createDatabasePlugin` an in-memory
factory that records every inner `getBundles()` call, so the recorded query shape, row order and
pagination object all come out of real upstream code.

Two details of that contract are easy to lose and are recorded explicitly:

- `createPaginatedResult` **omits** `nextCursor`/`previousCursor` rather than setting them to
  `null`, so each case also records `paginationKeys` — the exact key set upstream produced.
- Cursors are compared with JS truthiness, so an **empty-string** cursor is treated as absent.
- `limit` and `page` are parsed by *different* rules: `limit` is bounded to 1..=100 and 400s
  outside it, while `page` has **no upper bound** and a different 400 message. Both go through
  JS `Number()`, so `+5`, `1e2`, `0x10`, `50.0`, `" 7 "` and `007` are all accepted while `""`,
  `"  "`, `-0` and `1_000` are rejected.
- `idIn` and `targetAppVersionIn` are **repeated** parameters (`?idIn=a&idIn=b`) read with
  `searchParams.getAll`. `?idIn=a,b` is a single id containing a literal comma — commas are
  never separators. This matters for `targetAppVersionIn`, whose values legitimately contain
  spaces (`>=1.0.0 <2.0.0`).
- `platform` on `GET /bundles` 400s on anything outside `ios`/`android`; it does not fall
  through to an empty result.
- `enabled` and `targetAppVersionNotNull` accept only the exact strings `true`/`false` — no
  `1`/`0`, no case folding, no trimming — and the 400 names the offending key, so
  `targetAppVersionNotNull` and `enabled` produce different messages. Note this is the
  opposite of the integer params, which run through JS `Number()` and *do* tolerate padding.
- **Two different emptiness rules live in the same handler.** `targetAppVersion` and
  `fingerprintHash` go through `parseNullableStringSearchParam` and are folded in with
  `!== undefined`, so `?targetAppVersion=` is a real filter on the empty string and the exact
  lowercase `?targetAppVersion=null` means SQL `IS NULL` (`NULL`, `Null` and `" null "` are
  literal strings — the comparison is case-sensitive and untrimmed). `channel` is folded in
  with JS truthiness instead, so `?channel=` drops the filter entirely while `?channel=null`
  is the literal four-character string and `?channel=0` is kept (a non-empty string is truthy
  in JS). The `nullableStringParams` and `truthyStringParams` fixture groups exist to keep
  these two rules from being collapsed into one.
